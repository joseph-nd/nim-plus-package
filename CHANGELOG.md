# Changelog

All notable changes to this module will be documented in this file. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

**The Commander's Combat Tactics, connected to the Combat Dice that pay for them.** The system models the resource faithfully — *Fit for Any Battlefield* carries a `chargePool` (`@strength` dice, refreshed `onInitiativeRolled`, `dieSize: "d6"`) plus the `modifyPool` rules that upgrade it to d20, and a charge pool with a die size is the system's own "roll-on-spend" shape. What it does not carry is anything connecting that pool to the five Combat Tactics, whose items ship as descriptive text with empty `rules` arrays, or anything implementing "Combat Dice are lost when combat ends". So a Combat Die was rolled from a pip on the sheet, into chat, detached from the attack it was meant to modify, and last fight's dice were still sitting there at the start of the next one.

Everything below sits behind the existing **Enable Class Automation** setting.

### Added
- **Combat Tactic picker in the activation dialog.** Any weapon activation by a Commander gains a **Combat Tactic** row listing the tactics that character actually chose, filtered to the weapon in hand — *Lunging Strike* and *Sweeping Strike* name your Reach, so they are melee-only. A live note reports exactly what choosing one will roll, what it will do, and what it will cost.
- **The tactic's Combat Die is rolled into the attack's own damage roll**, so it shares the card, the tooltip and the single *Apply Damage* button rather than arriving as a second, unattached roll. **Lunging Strike**'s *"2× a roll of your Combat Die"* is emitted as one die doubled rather than two dice — the same average, a wider spread, and what the tactic says; **Heavy Strike** adds one die; **Sweeping Strike** adds nothing and only needs a die spent. The part of the tactic that is not damage (Heavy Strike's push and its size scaling, Lunging Strike's +1 Reach, Sweeping Strike's area and its second action) is posted as a rider note.
- **Sweeping Strike's *"this attack does not miss on a 1"*** is applied to the roll itself, so the chat card resolves as a hit rather than requiring the table to override a printed miss.
- **The die is spent only when the tactic did something.** *Heavy Strike* reads "when you hit", so a miss costs nothing, rolls nothing, and says so on the card. The pool is re-read when the roll lands rather than trusted from the dialog's snapshot, so a die spent elsewhere while the dialog was open cannot be spent twice.
- **Inerrant Strike, offered on the miss it answers.** It cannot be declared in advance, so it is a prompt: miss an attack while a Combat Die remains and you are asked whether to spend one. Accepting rerolls the attack *in place*, which re-applies the Primary Die's own advantage/disadvantage and explosion modifiers through Foundry rather than reimplementing them, then raises the Primary Die by 1 (carrying any excess past the die's maximum as a flat term, the way the system's own `primaryDieModifier` preset does) and rolls a Combat Die into the damage. A reroll into a crit chains into **Sneak Attack** exactly as a natural crit does. Results are snapshotted before the reroll and restored if any term fails, so a failure leaves the original roll untouched rather than half-rerolled.
- **Combat Dice are discarded when combat ends.** The shipped pool refreshes itself at Initiative and declares nothing for the other end of the fight, so unspent dice survived the encounter. The charge subsystem already dispatches an `encounterEnd` trigger with nothing listening for it, so a single `encounterEnd` / `set 0` recovery entry — added to the rule that is already there, in memory — is the whole fix.
- **Commanding Presence now costs a Combat Die.** It is listed among the Combat Tactics but is an Action rather than an attack rider, and nothing in the shipped feature made it cost anything. It is blocked with an empty pool and spends a die on use, driven off the system's own `preUseItem` / `useItem` hooks rather than another prototype patch. Its die is never rolled: the save DC is 10+STR, so the value is never read.
- **The sheet's Combat Dice row steps aside out of combat.** The system rails every roll-on-spend pool whenever it has capacity, which is right for a resource you carry around and wrong for one that only exists inside a fight. Inside an encounter the row stays visible even at zero, because "none left" is worth knowing.
- **The subclass features that change the Combat Dice pool now do.** Four shipped with empty `rules` arrays, so their pool text did nothing:
  - *Seasoned Combatant* (Champion of the Pit, 7) — **+1 max Combat Dice**.
  - *Relentless Assault* (Champion of the Siege Breaker, 11) — **+2 max Combat Dice**, and rolls with advantage.
  - *Master at Arms* (Champion of the Pit, 15) — rolls with advantage.
  - *Single-Minded Fighter* (Champion of the Arena, 3) — *"you forego all Commander's Orders; whenever you would choose one, gain +1 max Combat Die instead"*. Commander's Orders are chosen twice at level 2 and once each at 6, 8, 10, 12 and 16, so this is a ladder of `modifyPool` rules reaching **+7** at level 16. (Coordinated Strike! is a class feature rather than an Order, so it is not converted.)
- **Foregone feature groups are no longer offered or granted.** *Single-Minded Fighter* gives up Commander's Orders entirely, so the **Commanders Orders** group is taken out of the level-up window and any Order is refused at creation — by whatever route, including a drag onto the sheet. The level-up window will not submit until every selection group has its picks, and that check is Svelte state nothing outside the component can reach, so a pick is made on the character's behalf purely to satisfy it and then discarded by the creation guard. Gaining the feature also offers to remove the Orders already on the sheet, since those are what its extra Combat Dice compensate for — offered rather than done, because deleting a player's features silently is not this module's call. Driven by a `foregoesFeatureGroup` module flag naming the group, so it is not specific to Orders or to this subclass.
- **"You roll Combat Dice with advantage" is applied to the roll.** A tactic's die becomes `2dN kh1`, and the dialog's spend row says so. Driven by a `combatDiceAdvantage` module flag on the feature rather than by its name, so a subclass added later is picked up with no code change.
- **A Combat Tactic can be chosen at a subclass level.** *Seasoned Combatant* reads "choose a Combat Tactic", but the level-up window builds its selection groups from an index keyed by class identifier and level — the core tactics are registered at 4/6/8/10/12/16 and a subclass cannot add itself to that list, since subclass features are always auto-granted rather than offered. A **Combat Tactic (Choose one)** section is added to the level-up window instead, alongside the existing Feats section, and the chosen tactic is granted on confirm. The tactics offered are the real documents from whichever pack ships them, found by their own `class`/`group` fields rather than by name, so homebrew tactics appear too; the trigger is a `grantsCombatTactic` flag on the granting feature, so this follows the content.
- **Commanding Presence is republished as a Commander's Order.** It ships under Combat Tactics, matching the rulebook — but that section's header promises *"1/attack, you can expend a Combat Die to add one of the following effects **to your attack**"*, and it is the only one of the five that is not an attack rider at all: a standalone Action with a WIL save. The module ships its own copy filed under `commanders-orders` at the levels Orders are chosen, so the level-up window offers and grants it through the system's own selection machinery with nothing intercepted, and the core card is hidden from the Combat Tactics group so the same feature is never on offer twice. This is a reclassification, not a rules change — it still costs a Combat Die. Two knock-ons worth knowing: it now competes with *Face Me!* and *Reposition!* rather than with the Strikes, and *Single-Minded Fighter* gives it up along with the rest of the Orders.

- **Master Commander now does what it says.** Another Commander feature shipped with no rules behind its prose, so neither of its mechanical clauses did anything. Both are now supplied: **+1 use of Coordinated Strike! at each of levels 5, 9, 13 and 17** (a `modifyPool` ladder predicated on level — the feature is granted once and never re-granted, since the level-up window filters out anything already owned, so the levels have to be predicates on that one copy), and **1 spent use regained when you roll Initiative** (an `onInitiativeRolled` recovery of `add 1`, which clamps at your maximum, so with nothing spent there is nothing to regain — exactly as written). The regained use is *"lost if not spent during that encounter"*, which no recovery can express because recovery values cannot go negative; it is taken back when the encounter ends only if the count is still exactly where the recovery left it. Spend anything during the fight and the granted use is the one you spent, and a count that has since gone up — a Safe Rest mid-encounter — is not docked. *"Attacks made from your Coordinated Strikes ignore disadvantage"* stays with the table: those attacks are rolled separately, and nothing connects them back to the order that prompted them.

### Changed
- **The advantage slider is taken off activations that roll nothing.** *Coordinated Strike!* is a free action that grants you and an ally an attack each; those attacks are rolled separately, with their own dialogs and their own advantage, so a slider on the order itself reads as though it will change them and changes nothing. It is hidden when an activation states damage or healing but has no dice anywhere in it — a positive test, so an activation that declares no formula at all is left alone in case it rolls through some path not visible from the dialog. Situational Modifiers and the primary-die fields are just as inert on a card like this, but they at least alter the number it prints.
- **Combat Dice are no longer offered on activations that cannot spend them.** The system lists every roll-on-spend pool with capacity on every activation dialog, so the Combat Dice stepper turned up on *Coordinated Strike!* — where a die has nowhere to go, since Combat Dice are only ever spent as a Combat Tactic on an attack, or by Commanding Presence. The row is now hidden wherever no tactic applies, the same way it already was on attacks, and the section heading goes with it if Combat Dice were the only pool on offer.
- **Spending a use from the tracker rail posts the feature's chat card.** Clicking the last lit pip is the feature being *used*, so it now goes through the sheet's own activation path — the same card you get from the Features tab, the same macro, the same refusal at zero — instead of quietly moving a number. The spend is left to whoever owns it: a feature that declares a charge consumer has one deducted by the system as part of the use, and only a feature without one has its counter moved afterwards, so a use can never cost two. The pips' other jobs are unchanged and stay silent: clicking a dim pip restores up to it, and clicking a lit pip further down sets the count without using anything. Tooltips now say which of the two a click will do.
- **The dialog's Spend Pool Dice stepper for Combat Dice is replaced, not shared.** The system draws every roll-on-spend charge pool as a stepper that adds `+Nd6[Label]` to the damage and decrements the pool; for this pool that control is wrong on its own terms, since a Combat Die is only ever spent *as* a Combat Tactic and a free-floating "spend two of them" stepper invites breaking the 1/attack rule the dice exist for. Choosing a tactic brings the same row back read-only — the pool's own die icon and label, then what the tactic will roll (`2 × 1d6`, `1d6`, or a plain die count for Sweeping Strike) where the stepper's count was, against the dice remaining. With no tactic selected the row is not there at all, and the section's heading goes with it if Combat Dice were the only pool on offer. Commanding Presence, which spends a die on use, shows the same read-only row in place of the stepper. Built from the system's own class names and anchored optionally, so if the markup moves in a future version the worst case is that the native stepper stays and no row of ours appears.
- **Feature use counters leave the sheet's tracker rail when combat ends.** The rail mirrors counters like *Coordinated Strike!* precisely because they are spent mid-combat, often on another creature's turn; out of combat it is a permanent overlay for something nobody is about to click, and the Features tab still carries every counter.
- **A fight counts as under way as soon as it is on the combat tracker**, rather than only once Begin Combat has been clicked. Foundry's `started` is a derived getter meaning "round 1 or later", so gating on it made the rail — and the Combat Dice row, which shares the test — disappear while the GM was still dragging combatants in, then reappear a click later. Combatants arriving and leaving now redraw both. The other end needed no change: ending an encounter deletes it from the tracker outright.

### Technical
- Nothing about the pool itself is rebuilt: the resource stays the `chargePool` the content ships, with its initiative refill and its d8/d10/d12/d20 `modifyPool` upgrades untouched, so level scaling continues to come from the content. The one addition is the recovery entry above, and it stands down the day the content declares an `encounterEnd` recovery of its own.
- The recovery is written to the prepared rule instance, never to `system.rules`, so it is rebuilt on every data preparation and evaporates when the module is turned off — at which point the system's next sync pass rewrites the persisted pool state from the rules and the entry disappears with it. Because the charge subsystem builds its effective pool map from the live rules rather than from the flag, the entry is in force from the moment the module loads, with no migration step.
- The pool is located by a fuzzy identifier/label match against flag state rather than a hardcoded rule id, and the tactics by matching the actor's own feature identifiers *or* names, so renames and homebrew copies still resolve. Every DOM anchor in the dialog and on the tracker is optional — a missing one means the control does not render and play continues unchanged.
- The crit-explosion replay written for Vicious Opportunist is now shared with Inerrant Strike, the other feature that pushes a Primary Die to its maximum after the dice have landed.
- `appendDamageToRoll` no longer tags operator terms with roll flavor. A term serialises as `expression[flavor]`, so the `*` in Lunging Strike's doubled die would have produced `*[Lunging Strike]` and broken formula reconstruction on other clients.
- A tactic armed by the dialog is dropped if the damage roll that follows is not part of a tracked activation, so an arm can never survive to a later swing.
### Fixed
- **Every injected rule was lost on world load, and stayed lost until the feature was re-granted.** The patch that lets the module supply a rule during data preparation was installed from the `setup` hook — but `Game#setupGame` initializes all world documents *before* it fires `setup`, and a Nimble item builds its rules exactly once, its `prepareData` short-circuiting on an `initialized` flag from then on. So the patch never reached a single item that already existed: a feature worked perfectly the moment it was granted, and was quietly unautomated after the next reload. Nothing looked broken in the meantime, because the pool state the system had already written to the item stayed there — until the next level-up, when the system rebuilt that state from the rules it could see, found none, and dropped the pool. *Coordinated Strike!* losing its use counter on levelling was this. The patch now goes in at `init`, before any document exists; if the system registers its document classes first, anything prepared in between is rebuilt, and a world carrying pool state written while the rules were missing is re-synced once on load.
- **The Combat Tactic section never appeared at level-up.** The subclass whose features grant it was resolved from the subclass item's `system.identifier`, but the level-up window keys its own lookup on the subclass item's **name**, slugified — which is not the same value and is not always populated. The module now derives the group exactly the way the window does. The `grantsCombatTactic` flag is also read from the feature document rather than from the compendium index, since an index only carries the fields it was asked for and module flags are not among the ones the system registers.
- **Features already on a character sheet now get their pool rules repaired.** An item on a sheet is a snapshot of the compendium as it was the day it was granted and is never updated afterwards, so a Commander who took *Seasoned Combatant* before its `modifyPool` rule existed would have carried a feature that does nothing for the rest of the campaign. The three pool-changing features are now recognised by name at data-preparation time and given their rules if the copy on the sheet predates them — skipped entirely when the item already carries a Combat Dice `modifyPool`, so the content always wins and nothing ever doubles. *Master at Arms* and *Relentless Assault* are likewise recognised by name for the advantage they grant, not only by their flag.

## [0.7.0] - 2026-07-26

**Class quality-of-life automation**: four core-class features that previously required the player to remember a counter or to make a second manual roll now handle themselves. All of it sits behind a single new world setting, **Enable Class Automation** (`enableClassAutomation`), which defaults to **on**; turning it off restores fully manual play.

Nothing here adds an item to pick or writes to your characters. Where a feature's mechanics are already expressible in the system's rules engine but the shipped feature carries no rule, the module builds that rule from the system's own rule class and inserts it into the feature's in-memory rules map. `system.rules` — the persisted source — is never touched, the rule is rebuilt on every data preparation, and each injector no-ops if an equivalent rule is already present, so a future system-side fix silently wins.

### Added
- **New setting — Enable Class Automation.** *Game Settings → Configure Settings → Nim+ Package*. Gates every automation below.
- **The Cheat — Vicious Opportunist (one-roll crit upgrade).** Melee weapon activations by a Cheat who owns the feature gain a **Vicious Opportunist?** checkbox in the system's roll dialog (declaring the target Distracted). The attack is then rolled once, respecting advantage/disadvantage, and resolved automatically: a Primary Die between 2 and max−1 is raised to its maximum *in place* — the crit explosion is rolled onto the same chat card, so the card, the effect tree's critical-hit branch, and Dice So Nice all see one coherent critical hit. A **natural crit** is announced as such and a **miss** is reported as ineligible; neither spends the 1/turn use. The budget is keyed to the combat tracker's `combat:round:turn`, so it re-arms on its own as turns pass, and is unrestricted outside combat.
- **The Cheat — Sneak Attack (crit prompt).** Because the trigger is a crit, this is a prompt rather than an opt-in: any crit by a Cheat who owns the feature and still has the 1/turn use opens a dialog offering the level-appropriate dice. Accepting appends them to the attack's *own* damage roll — same chat card, same roll tooltip, one *Apply Damage* — rather than posting a second card. Declining keeps the use. A Vicious Opportunist upgrade produces a real crit, so the two chain. The scaling table (1d6 → 3d20 across levels 1–17) is parsed from the feature's description, with the printed table as a fallback, so upstream rebalances and homebrew edits are followed automatically.
- **The Commander — Coordinated Strike! (use counter).** The "INT times per Safe Rest" limit exists only in the feature's prose. The module supplies the missing `chargePool` (`@intelligence`) and `chargeConsumer` on the core order itself, so the system's charge subsystem takes over: a use is spent on activation, the order is blocked at zero, and a **Safe Rest** refills it.
- **Judgment Dice now respect the features that modify the roll.** **Reliable Justice** (Sacred Decree: *"whenever you roll Judgment Dice, roll with advantage — roll one extra and drop the lowest"*) and **Aura of Zeal** (Oath of Vengeance: *"whenever you roll Judgment Dice, roll 1 more"*) both ship with empty `rules` arrays and were previously ignored. Aura of Zeal is supplied as a `modifyPool` rule with `maxDelta: '+1'` — identical to the rule Radiant Judgement's own level-14 rider already uses for the same sentence — so it stacks correctly with that rider and with the die-size scaling. Reliable Justice is applied at roll time by mutating the pending flag write, so the pool is written once with the kept dice rather than briefly holding the un-advantaged set, and the chat card reports the extra die and the dropped one. Because a `preUpdate` hook cannot await, the extra die is rolled with `Roll#evaluateSync`; if that is unavailable (Foundry's manual dice fulfillment makes every roll an async prompt) the decree is skipped for that roll and logged, rather than half-applied. **Maximum Judgment** and **Avenger** remain manual — they alter dice you already hold on triggers that need a table call.
- **Feature use counters on the character sheet's tracker rail.** The system's own rail (the left-edge flyout that shows an Oathsworn's Judgment Dice) deliberately excludes charge pools without a die size, on the grounds that they are already drawn by `ChargeIndicator` on the Features tab. For a free action spent during another creature's turn that is the wrong place to look, so class-feature use counters are now mirrored onto the rail: the feature's own icon as the badge, one pip per use, click a lit pip to spend down to it or a dim one to restore up to it. Restricted to pools sourced from `feature` items, so charged inventory items are unaffected. Styling is expressed entirely in the rail's own CSS custom properties, so it follows the sheet theme, and the pips are re-derived from flag state on every render and on the system's `chargePool.changed` / `chargePool.recovered` hooks.

### Changed
- **The Oathsworn — Radiant Judgement, reworked.** The first implementation appended the pool's total to the weapon's damage formula from outside, which double-counted against the activation dialog's own dice-spending UI and presented a choice of *which* dice to spend that the feature does not offer. Replaced with the `diceConsumer` rule the shipped feature is missing — `autoBonus` mode, melee-only — so the system itself adds every face to qualifying melee damage and renders the pool as a read-only summary row. The module now only closes the two remaining gaps: `autoBonus` pools never decrement (by design, for snowballing pools like Fury Dice), so the pool is cleared after a swing that actually carried the bonus, hit or miss as written; and the dice are now rolled when an attack is aimed at the Oathsworn — **hit or miss** — instead of only when the GM applies damage, with a chat card announcing the result. Because the roll and the expenditure are now detected from the resulting flag write and the roll formula respectively, holding **Alt** to skip the activation dialog skips the bonus *and* leaves the dice unspent, rather than burning them for nothing.
- **Pack counts:** unchanged at **447** class features and **1,020 documents** — the counter is now injected onto the core order, so the previously planned `Coordinated Strike! (Tracked)` pack entry was dropped rather than shipped.

### Technical
- Every automation degrades to a no-op rather than breaking play if the Nimble system shifts underneath it: prototype wrappers always call through to the original inside a `try`/`catch`, are `__nimPlus*Patched`-guarded, resolve system classes by *capability* rather than by `constructor.name` (the system ships minified, so class names are mangled while method names survive), and derive hook names from `game.system.id` so `nimble-dev` builds work as well. Synthetic rules are built from `CONFIG.NIMBLE.ruleDataModels`, so an unregistered rule type turns the feature off instead of throwing. Where the system already implements a mechanic — charge pools, dice-pool refills and consumption, vicious explosion chains — it is called rather than reimplemented.

## [0.5.0] - 2026-07-13

### Added
- **Expanded Equipment (67 mundane items)**, adapted from the *Expanded Equipment* zine by Danny Rowe, in five new **Nim+ Items** compendium folders: **Shields** (8), **Armor** (15), **Bludgeoning Weapons** (13), **Piercing Weapons** (18), and **Slashing Weapons** (13).
